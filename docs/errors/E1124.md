# E1124: invalid `&`-block argument

## Why
Block Tier-2 adds two `&`-forms of a block **argument** (as opposed to a
`&block:` *parameter*, see [E1119](E1119.md)):

- `&:symbol` — to-proc sugar. `xs.map(&:upcase)` desugars to
  `xs.map { |x| x.upcase }`.
- `&block` / bare `&` — block-forwarding. Inside a function that received a
  block, `g(&block)` forwards that block on to `g`.

Both are only meaningful as the **last argument** of a call, where they fill the
call's block slot — exactly like a trailing `do … end` / `{ }`. This error
fires when the form is misused:

1. A `&`-block argument is not the last argument of the call.
2. A `&block` / `&` forward appears in a function that has **no block** to
   forward (no `&block:` parameter and no `yield`).

See [docs/decisions/ruby-block-semantics.md](../decisions/ruby-block-semantics.md)
(Tier-2, staged).

## Example
```rx
# (1) not the last argument
xs.zip(&:to_s, other)      # error[E1124]: `&:to_s` must be the last argument

# (2) nothing to forward
def m
  g(&block)                # error[E1124]: `m` has no block parameter to forward
end
```

## Fix
Put the `&`-block argument last, and only forward a block from a function that
actually declares or receives one:

```rx
xs.map(&:to_s)             # last argument — OK

def m(&block: Fn[(Int) -> nil])
  g(&block)                # `m` received a block; forwarding is OK
end
```

## Notes
- `&:symbol` produces a **one-argument** proc (`{ |x| x.symbol }`); it does not
  cover multi-argument method-references.
- Ordinary `&expr` in argument position is still a by-reference borrow — only
  `&:sym`, `&block`, and a bare `&` are treated as block arguments.
