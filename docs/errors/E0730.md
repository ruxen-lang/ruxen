# E0730: `str` is not a type; use `String` (owned) or `&String` (borrowed)

## Why

Ruxen has exactly one string type pair:

- **`String`** — an owned, heap-allocated string. It is dropped (freed) at the
  end of its scope.
- **`&String`** — a borrowed reference to a `String`. No ownership flows
  through it, so nothing is freed when it goes out of scope.

There is no separate `str` / `&str` type. It used to exist as a parallel
spelling of a borrowed string, but at the machine level a `String` and the old
`&str` were the *same* representation (a bare null-terminated `char*` — there
is no length/capacity header), so the second type added nothing but confusion
and a class of drop-safety hazards. It was removed
(`docs/decisions/one-string-type.md`).

A type annotation that spells `str` (or `&str`) is therefore rejected with
E0730 at name-resolution time.

## Example

```ruxen
# error[E0730]: `str` is not a type in Ruxen
def greet(name: &str) -> String
  "hello #{name}"
end
```

## Fix

Use `&String` for a borrowed string parameter (the common case — the caller
keeps ownership, the function only reads it), or `String` for an owned one (the
function takes ownership):

```ruxen
def greet(name: &String) -> String
  "hello #{name}"
end
```

A string literal is born as an owned `String`, so passing `"world"` to a
`&String` parameter works directly — the call site borrows it for you:

```ruxen
puts greet("world")
```

## Notes

- A field, return type, or local annotation spelled `str` is rejected the same
  way: write `String` (owned) or `&String` (borrowed).
- `&"literal"` is a `&String` borrow of an owned string literal.
- There is no behavioural difference at the C ABI: both a `String` and a
  `&String` cross the boundary as a single `char*` pointer.
