# E0723 — duplicate `layout tagged` enum in scope

## Summary

Two enums declared in the same scope both carry an in-body
`layout tagged` directive AND share the same name. `layout tagged`
pins variant declaration order as the runtime tag assignment (tag
0..N follows source order), so two enums sharing a name would
silently disagree on which tag values mean what — the resolver
refuses the second declaration outright:

```
[E0723] error: duplicate `layout tagged` enum `IoErrorKind` in scope
```

The error always lands on the **second** declaration. The first
declaration is the accepted one (matching the project's
"tags are append-only" invariant — see
`feedback/project_riven_tagged_enum_widening_pattern`).

## Common causes

1. **Accidental re-declaration during a refactor.** Two files (or
   two `mod` blocks in the same module) both declare
   `enum IoErrorKind` with `layout tagged`. Pick the canonical
   site and delete the duplicate.

2. **Copy-paste from a stdlib reference.** The stdlib's tagged
   enums (`IoError`, `IoErrorKind`, `ConnectError`) are declared
   exactly once each. A user fixture that mirrors the same enum
   name as a learning exercise hits this code; rename the user
   enum (e.g. `MyIoErrorKind`) or drop the `layout tagged`
   directive on it.

3. **Stale generated code left in-tree.** A code generator that
   emits a tagged enum into a file the source tree already
   provides. Delete the generated file or teach the generator to
   skip already-present targets.

## How to fix

- Decide which declaration is the canonical one.
- Delete the other (or rename one of the two).
- If both declarations are truly distinct types that happen to
  share a name, scope them: put one inside a module so the
  qualified names differ.
- If only one of them needs the tag pin (the other doesn't go
  through FFI / runtime dispatch), drop `layout tagged` on the
  non-pinned one. E0723 only fires when **both** are tagged.

## Background

The Riven runtime dispatches on enum tags via a switch over
the raw `i32`. The tag for variant N is N — its position in the
source-order variant list at compile time. The
`layout tagged` directive is the user-facing surface that
declares "this enum is going through that runtime dispatch, so
its variant order is load-bearing." Two enums sharing the
declared name in the same scope would lose that invariant
(monomorphization picks one arbitrarily and the runtime tag
table becomes ambiguous), so the resolver rejects the second
one. The first declaration wins because tag order is
append-only — silently accepting the second would let a
later-added duplicate renumber tags 0..N out from under
already-built objects.

E0724 is **reserved** for the matching `layout flat_heap_struct`
link-time layout-mismatch check; it is not emitted today (the
runtime `riven_<class>_layout_check` symbol gating it does not
yet exist) but is documented here so contributors landing on
this page see the full reserved range.
