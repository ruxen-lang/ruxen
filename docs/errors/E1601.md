# E1601: circular path dependency between workspace members

## Why
Two or more workspace members depend on each other through `path` (or
intra-workspace name) dependencies, forming a cycle. The build cannot
proceed because there is no leaf to compile first.

The diagnostic is the same shape as the legacy path-cycle detector,
but tagged `E1601` when every node on the cycle is a workspace
member — that way contributors who hit this from a misconfigured
`[workspace]` land on this page instead of debugging it as a generic
path-dep issue.

## Example
```toml
# pkg-a/Ruxen.toml
[dependencies]
pkg-b = "0.1.0"   # intra-workspace name resolution → ../pkg-b

# pkg-b/Ruxen.toml
[dependencies]
pkg-a = "0.1.0"   # cycle back to pkg-a → E1601
```

## Fix
Break the cycle. Common approaches:

1. **Extract shared types into a third member** that both depend on
   (e.g. `pkg-a` and `pkg-b` both depend on `pkg-common`).
2. **Invert one direction** by replacing one of the dependencies with
   an indirection (callback, trait/mixin abstraction) defined in the
   smaller of the two members.
3. **Merge** the two members if their coupling is truly mutual.

## Notes
- Detection happens during transitive `resolve_deps` recursion.
- Companion code: [E1600](E1600.md) — workspace member not found.
