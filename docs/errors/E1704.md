# E1704 — invalid regex pattern

The pattern inside a `/pat/flags` literal failed the compiler's
compile-time validation pass. The pattern is checked against the
same flag set Ruxen exposes at the surface (`i m s g x`); the
runtime engine is PCRE2.

## Example (rejected)

An unclosed `[` character class is reported as E1701 instead, since a
`/` inside `[...]` does not close the literal.

Rejected with E1704 [implemented]:

```ruby
r = /(unbalanced/       # E1704: missing closing `)` for group
r = /\q/            # E1704: unknown escape sequence
```

## Why at compile time?

`/pat/flags` literals must compile cleanly for the program to run —
there is no recovery path (the literal is hoisted to a single
module-init PCRE2 compile). Catching the error at compile time gives an
exact source span and a readable diagnostic, rather than panicking
at program start with a stack-trace into the C runtime.

## Fix

Close the open construct or correct the escape.

Compiles [implemented]:

```ruby
r = /a[bc]/
r = /(balanced)/
r = /\d/       # `\d` is the digit class
```

For a runtime-built pattern that may or may not compile, use
`Regex.new(pattern, flags)`, which returns
`Result[Regex, RegexError]`.

Compiles; `Result`, `Ok` and `Err` are [deprecated], replaced by `raise` and `begin/rescue`, [planned](../../TODO.md#t-exceptions):

```ruby
pattern = "a(b"
case Regex.new(pattern, "")
in Ok(r) then puts "ok"
in Err(e) then puts "bad pattern: #{e.message}"
end
```

## Caveats

- The compile-time validator covers most common
  PCRE2 syntax, but a small set of PCRE2-only constructs (some
  lookaround flavours, certain backreference forms) typecheck
  successfully here and only fail at module-init time. When that
  happens the runtime panic message names the literal source span
  so the fix-site is unambiguous.
