# E1704 — invalid regex pattern

The pattern inside a `/pat/flags` literal failed the compiler's
compile-time validation pass. The pattern is parsed by
`regex-syntax` against the same flag set Ruxen exposes at the
surface (`i m s g x`); the runtime engine is PCRE2.

## Example (rejected)

```ruxen
let r = /a[bc/       # E1704: missing closing `]` for character class
let r = /(unbalanced/   # E1704: missing closing `)` for group
let r = /\q/        # E1704: unknown escape sequence
```

## Why at compile time?

`/pat/flags` literals must compile cleanly for the program to run —
there is no recovery path (the literal is hoisted to a single
module-init PCRE2 compile). Catching the error at typeck gives an
exact source span and a readable diagnostic, rather than panicking
at program start with a stack-trace into the C runtime.

## Fix

Close the open construct or correct the escape:

```ruxen
let r = /a[bc]/
let r = /(balanced)/
let r = /\d/   # `\d` is the digit class
```

For a runtime-built pattern that may or may not compile, use
`Regex.new(pattern, flags)`, which returns
`Result[Regex, RegexError]`:

```ruxen
match Regex.new(pattern, String.from(""))
  Ok(r) -> puts "ok"
  Err(e) -> puts "bad pattern: #{e.message}"
end
```

## Caveats

- The compile-time validator (`regex-syntax`) covers most common
  PCRE2 syntax, but a small set of PCRE2-only constructs (some
  lookaround flavours, certain backreference forms) typecheck
  successfully here and only fail at module-init time. When that
  happens the runtime panic message names the literal source span
  so the fix-site is unambiguous.
