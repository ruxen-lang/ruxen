# E1018: block parameter stored

## Why
A trailing block (`{ |x| ... }` / `do |x| ... end`) bound to a parameter
typed `Fn[...]` is a *block*: it borrows the variables it captures for the
duration of the call, and the caller frees them afterwards. Inside the
function, a block parameter (`&block: Fn[...]`, the implicit `yield` block,
or any `Fn[...]` parameter) may therefore only be:

- called: `block.(x)` or `yield x`;
- tested: `block_given?` / `block_defined?`;
- forwarded to another `Fn[...]` parameter: `each(&block)`, `apply(block)`.

Any other use keeps the closure past the call — a `let` binding, a field or
collection store, passing it to a non-`Fn[...]` parameter, returning it, or
capturing it in an owning proc or lambda — and is rejected.

An `async def` stores every parameter in the future it returns, so a
`Fn[...]` parameter of an async function is stored even when the body only
calls it: the future runs after the call that passed the block has
returned. Declare it `Proc[...]`.

The help line spells the storable type for the block's own signature, for
example ``declare `block` as `Proc[(Int) -> nil]` to store it``.

## Example
```rx
class Button
  handlers: Array[Proc[() -> nil]]

  def on_click(&block: Fn[() -> nil])
    @handlers.push(block)   # E1018: the block would outlive its captures
  end
end
```

## Fix
Declare the parameter as `Proc[...]`. A block bound to a `Proc[...]`
parameter is a proc: it owns its captures, so it can be stored.

```rx
class Button
  handlers: Array[Proc[() -> nil]]

  def on_click(handler: Proc[() -> nil])
    @handlers.push(handler)
  end
end
```

An async function takes a proc for the same reason:

```rx
async def run(f: Proc[(Int) -> nil]) -> nil
  f.(1)
end
```
