# E1112: `block_on` called inside `async` context

## Why
`std.executor.block_on(future)` drives a Future to completion on the
current thread by polling it in a loop. The single-threaded executor
(async sub-phase 3) IS that thread — calling `block_on` from inside an
already-async function or closure would have the outer `block_on`
holding the only thread while waiting for the inner future to
complete, but the inner future cannot make progress because no
thread is available to poll it. A guaranteed deadlock.

The check is symmetric to [E1110](E1110.md) (`.await` outside async)
— inverted: where E1110 says "you need an async context here", E1112
says "you cannot have a block_on in an async context".

## Example
```rx
use std.executor.block_on

async def inner() -> Int
  42
end

async def outer() -> Int
  let v = block_on(inner())   # error[E1112]
  v
end

def main
  puts "#{block_on(outer())}"
end
```

## Fix
Inside an async context use `.await` instead — that's the cooperative
suspension primitive the executor knows how to schedule:

```rx
async def outer() -> Int
  let v = inner().await   # ok
  v
end
```

`block_on` is only legal at the **top of an async stack** — the
synchronous entry point that bridges the rest of the program into
the executor. A typical shape:

```rx
def main
  let result = block_on(some_async_top_level())   # ok — main is sync
  puts "#{result}"
end
```

## Notes
- The check fires once per `block_on` call site whose enclosing
  function or closure is marked `async` (`async def` / `async ||`).
- Nested async closures inside a sync function are still async
  contexts — `block_on` inside them is still rejected.
- Spec: [docs/specs/stdlib/executor.spec.md](../specs/stdlib/executor.spec.md) §B6.
