# E0729: a closure / `Fn` value cannot be formatted into a string (no Display)

## Why

A closure (a lambda `-> { }`, a stored `{ }` block, or any `Fn` value) has
no text form: there is no meaningful way to print a function value.
Interpolating one into a string (`"#{f}"`) or otherwise asking for its
`to_s` is almost always a mistake.

The trap that makes this worth a dedicated diagnostic: a bare `do … end`
assigned to a name is **a closure literal, not an expression block**. So
`v = do ... end` does NOT bind `v` to the block's last value — it binds
`v` to the *un-invoked closure*, and the interpolation would otherwise
print a raw pointer address (silent garbage). E0729 turns that silent
garbage into a clear compile error.

## Example

Rejected with E0729 [implemented]:

```ruby
# error[E0729]: a closure / `Fn` value cannot be formatted into a string
v = do
  a = 1
  b = 2
  a + b
end
puts "#{v}"
```

Rejected with E0729 [implemented]:

```ruby
f = -> { 1 + 2 }
puts "#{f}"      # error[E0729]: `f` is a lambda, not its result
```

## Fix

If you wanted a *value* computed from several statements, use a helper
method (or an `if`/`case` expression, which do produce values).

Compiles [implemented]:

```ruby
def sum_two -> Int
  a = 1
  b = 2
  a + b
end

v = sum_two()
puts "#{v}"      # 3
```

A `do … end` (or `{ … }`) is a block to **attach to a call** — e.g.
`items.each do |x| … end`, `render do … end`. If you genuinely have a
closure and want its *result*, call it and interpolate that.

Compiles [implemented]:

```ruby
f = -> { 1 + 2 }
puts "#{f.call}"   # 3 — call, then format the Int result
```

> Design note: if Ruby-style *expression blocks* (a block that is itself a
> value) are ever added to Ruxen, the unambiguous spelling will be `begin … end`
> — `do … end` now firmly means "a block attached to a call". See
> `docs/TASKS.md`.
