# E1116: `Task.spawn` called outside `async` context

## Why
`Task.spawn(future)` enqueues a future into the per-thread executor's
task queue. The executor only runs while a `block_on(...)` call is
draining its top-level future on the same thread — that's the
window during which the pump call inside the block_on inline loop
drives queued tasks forward.

Calling `Task.spawn` from plain sync code that is NOT inside any
`async def` / `async {}` closure means there is no executor to
enqueue into. The task would be added to the queue, but nothing
would ever poll it: there is no surrounding `block_on` loop running
the pump call.

E1116 is the polarity-inverted twin of [E1112](E1112.md) (`block_on`
inside async — there's already an executor, calling another nests
deadlock). Both diagnostics fire at the same async-lowering pre-pass.

## Example
```rvn
async def long_running() -> Int
  42
end

def main
  let handle = Task.spawn(long_running())   # error[E1116]
  puts "#{handle}"
end
```

## Fix
Wrap the spawn call in an `async def` driven by `block_on`:

```rvn
async def driver() -> Int
  let handle = Task.spawn(long_running())   # ok
  # ... use handle.await once commit 2 lands, or poll TaskHandle.is_done.
  0
end

def main
  block_on(driver())
end
```

The spawned task runs while the surrounding `block_on` is draining
its top-level future. The block_on inline loop pumps the queue once
per iteration.

## Notes
- The check fires for both `Task.spawn(...)` and the raw form
  `Task.spawn_raw(...)`. Both reach the executor identically.
- v1 ships a single-threaded executor; spawned tasks run on whatever
  thread owns the `block_on` call. Spec
  [docs/specs/stdlib/task_spawn.spec.md](../specs/stdlib/task_spawn.spec.md)
  §B8 details the single-thread guarantee.
- Async closures inside sync functions create their own async scope
  — `Task.spawn` inside them is fine. The check uses the same
  scope-tracking shape as E1110 / E1112.
- Spec: [docs/specs/stdlib/task_spawn.spec.md](../specs/stdlib/task_spawn.spec.md)
  §B7.
