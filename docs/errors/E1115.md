# E1115: `.await` inside `while` / `for` body not yet supported

## Why
Each `.await` becomes a suspension point in the lowered state
machine. A `.await` in straight-line code generates a single new
state; a `.await` inside the body of a loop would need one state
per iteration plus a re-entry edge back to the loop head. v1 does
not yet implement loop-aware state-machine lowering, so the
compiler rejects the construct rather than miscompile it.

## Example
```rvn
async def drain(stream: Stream) -> Int
  var total = 0
  while stream.has_more
    let chunk = stream.next().await   # error[E1115]
    total = total + chunk
  end
  total
end
```

## Fix
Until v2 lands the loop-aware lowering, restructure the loop into a
recursive `async def`:

```rvn
async def drain(stream: Stream, acc: Int) -> Int
  if !stream.has_more
    return acc
  end
  let chunk = stream.next().await
  drain(stream, acc + chunk).await
end
```

Or collect the work into a `Vec[Future[T]]` and `join_all` once the
executor surface lands.

## Notes
- The check fires at every `.await` site whose enclosing loop body is
  a `while` / `while let` / `for` / `loop` body. `.await` inside an
  `if` or `match` arm within an async fn is fine — those branches
  become separate states per spec §B11.
- Spec: [docs/specs/syntax/async_lowering.spec.md](../specs/syntax/async_lowering.spec.md) §B11 (note on `while`/`for`) and "Reserved error codes" §E1115.
