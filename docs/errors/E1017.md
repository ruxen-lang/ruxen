# E1017: `include` of a type that is not a mixin

## Why
`include` mixes a mixin's methods into a class, struct or enum. The
compiler rejected this `include` because the name it was given is a
class, struct, enum or type alias, not a mixin. Ruby raises
`TypeError (wrong argument type Class (expected Module))` for the same
code.

A common cause is the old spelling `include Hash`: `Hash` is the
collection class. A class whose fields are all hashable is already
usable as a `Hash` key without any include (the [deprecated] `Hashable`
mixin is the old explicit spelling; Ruby's `hash` and `eql?` methods
are [planned](../../TODO.md#t-d8)).

## Example

Rejected with E1017 [implemented]:

```ruby
class Bar
  x: Int
end

class Foo
  include Bar        # error[E1017]: `Bar` is a class, not a mixin
end
```

Rejected with E1017 [implemented]:

```ruby
class Key
  id: Int
  include Hash       # error[E1017]: did you mean `include Hashable`?
end
```

## Fix
Include a mixin, or turn the shared behaviour into one. A mixin is
declared with `mixin` today, which is [deprecated] (it becomes a
`module`, [planned](../../TODO.md#t-module-mixins)).

Works today, with the `mixin` declaration that is [deprecated]:

```ruby
mixin Greeting
  def greeting -> String
    "hi"
  end
end

class Foo
  x: Int
  include Greeting
end
```

A hash key needs no include at all.

Compiles [implemented]:

```ruby
class Key
  id: Int
end

def index(h: Hash[Key, String])
  puts h.size
end
```

To reuse a class's behaviour, subclass it (`class Foo < Bar`) instead.
