# E1110: `.await` outside `async` function or closure

## Why
`expr.await` only has meaning inside an asynchronous context — an
`async def` method or an `async { ... }` closure. The compiler lowers
`.await` into a state-machine suspension point, which can only exist
inside a method that has itself been lowered to a Future state machine.

When `.await` appears in a synchronous context (top-level statements
included) the compiler has nowhere to attach the suspension to, so the
call is rejected before type checking. This catches the mistake at the
right span rather than producing a confusing type-mismatch later.

`async def` and `.await` are the working model today; Ruby's Fiber
scheduler (`Async do ... end`) is [planned](../../TODO.md#t-fibers) and
will replace them.

## Example

Rejected with E1110 [implemented]:

```ruby
async def fetch_count(id: Int) -> Int
  id * 2
end

n = fetch_count(42).await   # error[E1110]: top-level code is not async
```

## Fix
Move the `.await` into an `async def`.

Compiles [implemented]:

```ruby
async def fetch_count(id: Int) -> Int
  id * 2
end

async def report -> Int
  fetch_count(42).await     # ok
end
```

The synchronous program then drives the outer future with
`block_on(report())` (see E1112).

## Notes
- Wrapping a `.await` call inside a closure does NOT inherit the
  outer method's async context — the closure must itself be `async`.
- The check fires once per `.await` site; multiple errors are
  emitted if multiple sites are illegal.
- Spec: [docs/specs/syntax/async_lowering.spec.md](../specs/syntax/async_lowering.spec.md) §B12.
