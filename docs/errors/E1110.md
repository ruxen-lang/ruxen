# E1110: `.await` outside `async` function or closure

## Why
`expr.await` only has meaning inside an asynchronous context — an
`async def` function, an `async ||` closure, or an `async { ... }`
block. The compiler lowers `.await` into a state-machine suspension
point, which can only exist inside a function that has itself been
lowered to a Future state machine.

When `.await` appears in a synchronous context the compiler has
nowhere to attach the suspension to, so the call is rejected during
name resolution. This catches the mistake at the right span rather
than producing a confusing type-mismatch later.

## Example
```rx
def main
  fetch_user(42).await   # error[E1110]
end

async def fetch_user(id: Int) -> User
  ...
end
```

## Fix
Either mark the enclosing function `async`:

```rx
async def main
  fetch_user(42).await   # ok
end
```

…or call `block_on(...)` once an executor is available (sub-phase 3 —
not in v1 yet). Until the executor lands, top-level `main` may be
declared `async` for hand-poll testing as in the
`721_async_def_no_await_handpoll` fixture.

## Notes
- Wrapping a `.await` call inside a closure does NOT inherit the
  outer fn's async context — the closure must itself be `async`.
- The check fires once per `.await` site; multiple errors are
  emitted if multiple sites are illegal.
- Spec: [docs/specs/syntax/async_lowering.spec.md](../specs/syntax/async_lowering.spec.md) §B12.
