# E0722 — conflicting FFI declarations for the same C symbol

## Summary

Two `lib "X" ... end` or `extern "C" ... end` blocks declare functions
that target the **same C symbol** but disagree on the signature — the
number of parameters, a parameter type, or the return type differs.
Codegen would otherwise produce a mis-typed call against whichever
declaration the linker happened to resolve.

The diagnostic always points at the **second** (or later) declaration;
the first one wins, on the principle that re-stating a binding is the
common copy-paste mistake.

## Example that triggers E0722

```ruxen
lib "ruxen_runtime"
  def add_one as "ruxen_test_add_one"(x: I32) -> I32
end

lib "ruxen_runtime"
  # Second decl binds the SAME C symbol but disagrees on the return type.
  def add_one_64 as "ruxen_test_add_one"(x: I32) -> I64
end
```

```
[E0722] error: conflicting FFI declarations for the same C symbol
  `ruxen_test_add_one` — the earlier declaration's signature does not
  match this one
```

## Common causes

1. **Copy-paste drift.** A `lib` block was duplicated to extend a
   surface and one of the signatures fell out of sync with the
   runtime header.
2. **A Ruxen module and a stdlib `.rx` file both rebind the same
   runtime symbol.** After #06.8 stdlib self-hosting lands, library
   classes carry their own FFI bindings; a user package that also
   binds the same symbol (perhaps via direct `lib "<runtime-name>"`
   block) must match the stdlib's signature exactly.
3. **An `as "<sym>"` alias collides with a non-aliased Ruxen name.**
   `lib "X" def foo(...)` declares the C symbol `foo`; if another
   block writes `lib "X" def foo_legacy as "foo"(...)` with a
   different signature, this fires.

## How to fix

- Decide which declaration is canonical. Delete the other one, or
  unify their signatures.
- If both call sites genuinely need different Ruxen-side names
  pointing at the same C symbol, give them matching signatures.
- If the C symbol's signature **changed** in the runtime, update
  every declaration to match — and consider centralising the
  declaration in the appropriate stdlib `.rx` module so the
  binding only lives in one place.

## Background

A C symbol carries no type information at link time; the linker
resolves a call by name. The compiler's job is to make sure every
call site agrees on the symbol's type, otherwise the assembled
binary will pass arguments in the wrong registers or read the
return value at the wrong width. E0722 is the static check that
catches this before the linker silently merges incompatible
declarations.
