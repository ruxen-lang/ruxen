# E1701 — unterminated regex literal

A `/`-opened regex literal reached end-of-line or end-of-file before
the closing `/` was seen.

## Why

The `/pat/flags` syntax shares its opening token with the division
operator. Ruxen disambiguates the two positionally — `/` after an
expression context (lvalue, closing paren, identifier-bound value)
is division; `/` after a statement opener, operator, or `(`/`[`/`,`
is a regex. That disambiguation only works if the closing `/`
arrives on the same logical line: rolling a newline into the
literal would force the lexer to span tokens across the line break
and re-evaluate the positional decision at every subsequent line,
which would break the rule's "decide once, at the open" simplicity.
So an unclosed `/…` is a hard lex error, not a continuation.

## Example (rejected)

```ruxen
let r = /foo
        ^ E1701: unterminated regex literal
```

## Lexer rules

A `/` inside an open `[…]` character class doesn't close the literal,
so this also produces the error:

```ruxen
let r = /[a-z   # unclosed character class -> also unterminated
```

A `\/` is an escape — the `/` is consumed by the backslash and the
literal continues:

```ruxen
let r = /a\/b/   # OK: pattern is the four-byte string `a\/b`
```

## Fix

Close the literal:

```ruxen
let r = /foo/
let r = /[a-z]/
```

For runtime-built patterns whose body may legitimately span a string
boundary, use `Regex.new`:

```ruxen
let pat = Regex.new("foo", "").unwrap!
```
