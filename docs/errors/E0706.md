# E0706: where-clause const predicate is not satisfied

## Why
A const-generic type can declare a `where` clause that constrains
which instantiations are legal:

```rx
class Buf[const N: USize] where N > 0
  data: Int
end
```

At every use site that supplies a concrete const argument, the
predicate is evaluated against the binding map.  If the predicate
evaluates to **false** for the supplied value, the instantiation is
rejected here.

The supported predicate shapes are binary comparisons over
const expressions:

- `N > 0`, `N < 1024`, `N >= 1`, `N <= 64`
- `N == M`, `N != 0`
- `N + M == 8`, `(N + 1) > M` — any `+ - * /` arithmetic on the
  sides

## Example
```rx
class Buf[const N: USize] where N > 0
  data: Int
end

def take_zero(_b: Buf[0])   # error[E0706]: predicate `N > 0`
end                          # is not satisfied (N = 0)
```

## Fix
Pick a const argument that satisfies the predicate, or relax /
remove the `where` clause:

```rx
def take_one(_b: Buf[1])   # ok — 1 > 0
end
```

```rx
class Buf[const N: USize]   # no predicate — anything fits
  data: Int
end
```

## Notes
- Param-referencing instantiations (e.g. instantiating one
  const-generic class with another's const param) defer the check
  until the outer instantiation supplies the binding.  An
  unresolved param in either side of a predicate skips the check —
  it re-evaluates when the binding lands.
- Today the predicates parse only as part of class / struct /
  enum declarations.  Functions also accept a `where N > 0`
  predicate at the parser layer but the enforcement site is the
  type instantiation, not the call site (functions don't get
  monomorphized per-key in v1).
- Spec §B9 lists the `E-CONST-WHERE-FALSE` semantic label; this
  is the human-facing diagnostic code.
