# E1400: heap allocation in a no_std unit

## Why
A `no_std` build (tier 4.04) promises "I provide the host environment: don't
assume `malloc`, don't link libc." There is therefore **no global allocator**
wired in a no_std build (a user-supplied `global_allocator` is the staged
remainder). Constructing a heap-allocated value — `String`, `Array`, `Map`,
`Set` — would route through `ruxen_alloc` → `malloc`, which does not exist in
the no_std link. Rather than emit a binary that fails to link (or, worse,
silently allocate against a libc that isn't there), the compiler rejects the
construction up front with a located diagnostic.

What counts as a heap allocation: a string literal or interpolation, an array
literal / fill, a map literal, a collection macro (`array![…]`/`hash!{…}`), or
any call whose result type is one of the heap collection types. Borrows
(`&String`), reads, and pass-throughs do **not** allocate and are allowed.

See [docs/decisions/phase4-no-std-wasm.md](../decisions/phase4-no-std-wasm.md).

## Example
```rx
# compiled with `ruxen compile foo.rx --no-std`
def main
  let s = "hello"        # error[E1400]: heap allocation (string literal)
  let v = [1, 2, 3]      # error[E1400]: heap allocation (array literal)
end
```

## Fix
Use only stack/scalar values in a no_std unit:

```rx
def add(a: Int32, b: Int32) -> Int32
  a + b                  # no heap — fine in no_std
end
```

Or move the heap-using code behind a hosted build (drop `--no-std`), which
links the full standard library and its allocator.

## Notes
- A future no_std build will allow heap types **with** a user-provided
  `global_allocator` (the `alloc` tier). Until that lands, any heap construction
  in a no_std unit is rejected. E1401 (`std.*` import in a no_std unit) and
  E1402 (unsupported target triple) are reserved for that work and are not yet
  emitted.
- `wasm32-unknown-unknown` is a no_std target: the same rule applies (the wasm
  v1 path exports pure-integer math, no heap).
