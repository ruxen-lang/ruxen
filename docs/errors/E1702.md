# E1702 — `~=` operand type mismatch

The regex-match operator `~=` only accepts a `String` (or `&String` /
`Str`) on the left and a `Regex` on the right.

`~=` is [deprecated]: its replacement `=~` is [planned](../../TODO.md#t-match-op). Until it
lands, `~=` is the match operator, so the examples below use it.

## Example (rejected)

Rejected with E1702; `~=` is [deprecated]: its replacement `=~` is [planned](../../TODO.md#t-match-op):

```ruby
5 ~= /foo/                  # E1702: lhs is Int
s = "x"
s ~= "literal"              # E1702: rhs is String, not Regex
```

## Fix

Use a regex literal on the right.

Compiles; `~=` is [deprecated]: its replacement `=~` is [planned](../../TODO.md#t-match-op):

```ruby
s = "hello"
if s ~= /hel/
  puts "matched"
end
```

For a runtime-built pattern, use `Regex.new`.

Compiles; `~=` and `unwrap!` are [deprecated] (replaced by `=~`, [planned](../../TODO.md#t-match-op), and `x or raise`, [planned](../../TODO.md#t-truthiness)):

```ruby
s = "hello"
pat = Regex.new("hel", "").unwrap!
if s ~= pat
  puts "matched"
end
```

## Why a separate operator?

`==` would be ambiguous: comparing a `String` to a `Regex` for
equality is rarely useful, but the surface read of `s == /pat/` looks
indistinguishable from value equality. `~=` carries the "matches?"
semantics explicitly — readable as "tilde-equals", "matches", or
"squiggly equals".
