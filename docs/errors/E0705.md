# E0705: const-generic parameter type must be an integer or `Bool`

## Why
A `const N: TY` generic parameter binds a compile-time **value** of
type `TY` at every use site.  For two instantiations of the
surrounding type to be distinguishable, `TY` must support a stable
`Eq` contract, predictable bit-layout, and finite enumeration in the
const evaluator.  In v1 that narrows the legal set to:

- every integer family: `Int`, `Int8`, `Int16`, `Int32`, `Int64`,
  `UInt8`, `UInt16`, `UInt32`, `UInt64`, `USize`, `ISize`;
- and `Bool`.

Other types are spec non-goals:

- **`Float` / `Float32` / `Float64` (NG2)** — `NaN != NaN` breaks
  the `Eq` contract that `Hashable` and const-generic instantiation
  identity rely on.
- **`String` / `&str` (NG3)** — heap-allocated value-equality
  isn't a compile-time operation in v1.
- **User classes / structs / enums / tuples / Array** — even
  if their fields happen to all be valid const-param types, the
  composite identity is a v2 feature once `BuildHasher`-style
  per-type hashers exist.
- **`Char`** — close to working but deferred while encoding
  semantics get a v2 ruling.

## Example
```rvn
struct Buf[T, const N: Float]   # error[E0705]: must be an integer or `Bool`
  data: [T; 4]
end

struct Bag[T, const N: String]  # error[E0705]
  data: [T; 4]
end
```

## Fix
Re-declare the parameter with an integer family — `USize` is the
canonical choice for sizes and counts:

```rvn
struct Buf[T, const N: USize]
  data: [T; N]
end
```

For boolean toggles (e.g. a build-time feature flag) `Bool` is
accepted:

```rvn
class Logger[const COLOR: Bool]
end
```

## Notes
- The check runs in `Resolver::collect_generic_params` immediately
  after the type expression resolves, against
  `is_valid_const_param_ty(&Ty)`.  `Ty::Error` placeholders are
  treated as valid so this code doesn't stack on top of an
  upstream "unknown type" diagnostic.
- Spec §B8 catalogues this as `E-CONST-BAD-TYPE`; the human-facing
  code in the registry is **E0705**.
